# Ускорение ночной синхронизации CRM -> Postgres

Точка входа: `collect_leads_customers(is_full=True)` в `main.py`.
Порядок этапов остался прежний: покупатели -> сделки -> чистка. Изменено только выполнение этапов

## Что было дорого

1. **Поиск через `@>` по JSONB без индекса.** На каждого покупателя приходилось 1–2 запроса, на каждую сделку — 2. Каждый запрос полностью проходился по таблице и разбирал каждый JSON. Было Около 90 тысяч seq scan(проходов по всей таблице) за один прогон.
2. **Отдельный UPDATE и COMMIT на каждую сущность.** UPDATE отправлялся, даже если данные не менялись. При слиянии было 2 коммита, при чистке — до 5 на строку. Всего больше 70 тысяч коммитов.
3. **Чистка загружала всю таблицу разом** (`select(AbstractCustomer).all()`) вместе с полным `api_value`, а затем коммитила каждое поле каждой строки.
4. **Обновление сырым `jsonb_set`.** Раньше код менял строку в базе сырым SQL => Python об этом не знал и хранил старые данные. Работало это только потому, что после каждого коммита объекты помечались устаревшими(expire_on_commit=True) и перечитывались из базы.

## Что изменено

### Производительность
- **Индексы в памяти вместо поиска в БД** (`_load_index`). Перед каждым этапом выполняется два запроса: из JSON берутся только пары `general.id` / `general.login` -> `id` строки, без `api_value`. Дальше поиск идёт по словарям Python. По ходу работы словари обновляются: при создании строки и при слиянии.
- **Пачки по 500** (`_batches`, `_prefetch`). На пачку выполняется один SQL запрос. Дальше `session.get` берёт строки из identity map PostreSQL без запросов к самой базе.
- **Один commit на пачку.** Среднее между «коммит на каждую сущность» и «один коммит на весь прогон». При сбое CRM на середине уже обработанное сохраняется, как и раньше.
- **Изменения через ORM** (`_upsert`), а не сырым SQL. Если элемент не изменился, строка не трогается, и UPDATE для неё не отправляется.
- **Чистка пачками по id** (`WHERE id > :last ORDER BY id LIMIT 500`(строка 202)). В памяти одновременно не больше одной пачки.

### Исправленные ошибки и расхождения с правилами
| Было | Стало |
|---|---|
| Новый клиент добавлялся без `flush`, и в `ids_map` попадал `id = None`. В итоге `NOT IN (..., NULL)` в чистке не удалял ничего | `_create` делает `flush` сразу, благодаря ему `id` передается сразу |
| При слиянии `lead_action` делал `return` без значения: сделка не записывалась, вызывающий код падал на `None.id` | После слияния сделка записывается, функция всегда возвращает строку |
| После слияния `ids_map` удалённой строки не переносился, и чистка удаляла её покупателей из итоговой строки | `_merge` переносит `ids_map` и словари поиска на итоговую строку |
| В фильтре чистки проверялась переменная `l` вместо `c`: список целиком оставался или очищался. Пустое `name` приводило к падению | Проверяется каждый элемент, пустое имя обрабатывается(main.py:216-218) |
| Ошибка в сделке шла в лог, но чистка всё равно запускалась | Если хоть одна сделка не обработана, чистка не запускается. При любом другом сбое делается `rollback`, чистка не запускается |
| `custom_fields_values = null` из CRM ронял `get_field`, а для покупателей - весь прогон | В `Customer` и `Lead` подставляется пустое множество `{}` |
| `Lead` не читал `_embedded.contacts`, поэтому контакты, привязанные только к сделкам, удалялись чисткой | Читаются так же, как у `Customer` |

### Схема
Добавлены GIN-индексы(они разбивают на ключи: путь до значения+значение) `jsonb_path_ops` на `amo_customers` и `amo_leads` (`models.py`). Ночному прогону они не нужны. Они нужны для поиска другими частями системы по точному логину и названию: запросы вида `col @> '[{"general": {"login": "..."}}]'` идут по индексу. Связь сделка–покупатель хранится в одной строке `abstract_customer`.

Если таблица уже существует, индексы создаются вручную:
```sql
CREATE INDEX CONCURRENTLY ix_abstract_customer_amo_customers ON abstract_customer USING gin (amo_customers jsonb_path_ops);
CREATE INDEX CONCURRENTLY ix_abstract_customer_amo_leads     ON abstract_customer USING gin (amo_leads jsonb_path_ops);
```

## Что оставлено и почему

- **Формат JSON в полях и одна таблица.** Другие части системы скорее всего уже работают с таким форматом. 
- **GIN на всю колонку, а не только на `general`.** Индекс получается больше (в него попадает и `api_value`), и каждый UPDATE его обновляет. Но он работает с существующими запросами `@>` без изменения других частей кода. В другом случае нужно было бы переписывать эти запросы
- **`abstract_customer.py` не тронут.** Из него используются `get_customer_json`, `get_lead_json` и `dict_compare_merge`. Остальные функции синхронизации в моем задании не нужны, но их могут вызывать другие части системы.
- **Создание новой строки делает отдельный `flush`.** `id` нужен сразу, чтобы им пользовались следующие сущности той же пачки. В обычный ночной прогон новых строк немного. На первичной загрузке будет flush на строку, но без отдельных коммитов.
- **Удаление в чистке через ORM.** DELETE отправляются при `flush` пачки. Удаляемых строк за ночь немного, поэтому отдельный массовый DELETE не нужен.

## Оценка на 20 тыс. покупателей и 50 тыс. сделок(Оценка с помощью Claude)

Полный объём не прогонялся: клиента CRM в репозитории нет. Цифры ниже — расчётные.

**Запросы к Postgres**

| | Было | Стало |
|---|---|---|
| Поиск | ~90 тыс. запросов `@>`, каждый с seq scan | 4 запроса на индексы |
| Загрузка строк | вместе с поиском | ~240 `SELECT ... IN` (40 по покупателям, 100 по сделкам, ~100 в чистке) |
| UPDATE / INSERT / DELETE | на каждую сущность, ~70 тыс.+, плюс до 4 на строку в чистке | только изменённые, новые и удаляемые строки |
| COMMIT | >70 тыс. | ~240 |
| **Итого** | **порядка 300–400 тыс.** | **~500 служебных + записи изменённых строк** |

**Память процесса**

- Было: в чистке вся таблица в памяти вместе с `api_value`. Это линейный рост с размером таблицы: при нескольких КБ JSON на сущность — сотни МБ.
- Стало:
  - словари поиска: ~70 тыс. ключей, ~10–20 МБ;
  - `ids_map`: ~20 тыс. строк × 4 множества, ~20 МБ;
  - одна пачка из 500 строк с `api_value`;
  - текущая страница CRM.

  В сумме порядка десятков МБ, и от размера таблицы зависят только словари id и логинов.

# Исходное задание

Нужно ускорить ночную синхронизацию сущностей из CRM в Postgres.
Точка входа — `collect_leads_customers(is_full=True)`.
Нагрузка: 20 тыс. покупателей и 50 тыс. сделок.
Сейчас прогон делает отдельный запрос и commit на каждую сущность
и в конце ещё раз читает всю таблицу.
## Некоторые правила бизнес-логики
- Покупатель без логина пропускается.
- Покупатель ищется по id покупателя в CRM, иначе по логину среди уже сохранённых сделок.
  Если по логину нашлось больше одной записи, совпадение не используется.
- Сделка ищется по id сделки в CRM, иначе по логину среди покупателей.
  Если это две разные записи, они сливаются в ту, что нашли по сделке; вторая удаляется.
  Если не нашлось ничего, создаётся новая запись.
- После успешного полного прохода удаляются покупатели и вложенные
  сущности, которых не было в этой выгрузке, в том числе с «удалить» в имени.
- Если сбор прервался, удаление не запускается.
Падения и расхождения кода с этим списком нужно поправить.
Формат JSON в полях можно сохранить.
## Ограничения
- Python >= 3.9, Flask, SQLAlchemy, PostgreSQL.
- Celery, брокер и боевой API поднимать не нужно.
- Новые сервисы не добавлять. Схему хранения можно менять.
- Ночной прогон ищет покупателя и сделку по id CRM и по логину.
  Другие части системы ищут покупателя или сделку по точному логину и по названию.
  этот поиск писать не нужно, но выбранная схема должна его выдерживать.
  Также нужно поддерживать связь сделка-покупатель.
- Способ реализации на ваше усмотрение, правила выше обязательны.
